## Known Issues

- **🔴 SECURITY — password reset token is exposed in the API response, not emailed.** `POST /auth/forgot-password` returns the raw reset token directly (since no email/SMS service is configured — see architecture.md), and both frontends display it on-screen as a "dev mode" link. Anyone who knows a target account's email address can request and immediately use a reset token for that account — this is fine for local development with only test accounts, but **must be fixed (real email delivery, token removed from the response) before any account with a real user or real money exists.** Treat this as a hard blocker for any deployment beyond local dev/demo.
- **Discord webhook not yet configured** — `DISCORD_WEBHOOK_URL` is empty in `server/.env`. The code is fully wired (`sendDiscordMessage` fires on every admin-relevant event) and safely no-ops when the URL is blank, so nothing is broken — it just won't post anywhere until the user creates a webhook in their Discord server and adds the URL. Not something an AI session can do (requires the user's own Discord server access).
- **Push/voice/PWA-install unverified on a real device** — see the detailed note under Completed Tasks above. Everything up to the point of actual OS-level delivery is proven correct; the user should confirm on their own phone/desktop before relying on it.
- **No file-upload endpoint or UI for match-result screenshots** — `submit-result` accepts any URL string; a real player has no way to turn a screenshot into a URL yet. Needs a `multer`-backed upload endpoint (disk storage is fine to start, per [architecture.md](architecture.md)) plus a file-input widget on `royal-clans`'s match-submission form.
- **No auto-refresh on access-token expiry** in either frontend — a user must log back in every 15 minutes (the access token's lifetime) even though a working refresh-token cookie flow already exists server-side (`POST /auth/refresh`). Wiring an axios/fetch-interceptor-style "retry once after silent refresh" pattern is a reasonable follow-up, not required for MVP demo purposes.
- **Banning doesn't revoke live access tokens** (see Important Decisions) — same tradeoff as before, unchanged.
- **Quick Match needs a seeded room pool to work at all** — with zero rooms, every pairing attempt fails with a 503. Not a bug (the failure is clean and rolls back), but the admin must add rooms at `/rooms` first. Also note the throughput ceiling: N pooled rooms with a 30-minute cooldown allows at most N matches to start per 30 minutes; add rooms or lower the cooldown in `/settings` if players hit it.
- **Clan-wise leaderboard not built** — the PRD lists Global/Monthly/Weekly/Game-wise/**Clan-wise**; the first four exist, clan-wise is blocked on the Clan model which hasn't been built yet.

## Important Decisions

- **2026-07-24 — Database:** MongoDB + Mongoose (over PostgreSQL) — chosen for flexible schema fit with tournament/match data shapes.
- **2026-07-24 — Payments:** No payment gateway integration at launch. Users submit a manual bKash/Nagad transaction ID for deposits; an admin verifies and approves before the wallet is credited. Withdrawals are also manually processed by an admin. All fee amounts (tournament create fee table, entry service fee %, Quick Match fee %, withdrawal charge %) must live in an admin-editable `feeConfig` collection, never hardcoded.
- **2026-07-24 — Hosting:** Self-managed VPS (not a managed platform) — Nginx reverse proxy + PM2 process management + Let's Encrypt SSL, MongoDB on the same VPS initially.
- **2026-07-24 — Wallet integrity rule:** `walletBalance` is always derived from approved `transactions` — never directly editable by any endpoint, including admin ones. Admin balance corrections must themselves be a transaction (`adminAdjustment` type) for auditability. This is a hard rule in [rules.md](rules.md) and must not be relaxed for convenience.
- **2026-07-24 — Match validation:** Since Free Fire/Blood Strike have no official results API, results are confirmed via dual-screenshot submission with mutual winner selection; mismatches auto-route to an admin dispute queue rather than ever auto-resolving in anyone's favor. OCR/AI-assisted verification is a noted future upgrade, not part of MVP.
- **2026-07-24 — Scope:** Full platform vision expanded mid-session from a simple tournament-listing site to a full Esports Marketplace (Tournament Marketplace + Quick Match + Wallet + Clan/Ranking). Docs reflect the full vision; build order follows the MVP-first strategy above.
- **2026-07-26 — API docs:** Swagger (`swagger-jsdoc` + `swagger-ui-express`) chosen for API documentation, generated from JSDoc `@openapi` blocks co-located with each route (not a separately maintained spec file) so docs can't silently drift from the actual routes.
- **2026-07-26 — Wallet concurrency:** balance changes use conditional atomic `findOneAndUpdate` (not MongoDB session/multi-doc transactions), specifically to avoid depending on a replica-set MongoDB. Keep this pattern for future wallet-touching code unless the deployment target is confirmed to support multi-doc transactions.
- **2026-07-26 — Fee timing:** confirmed with the user that players creating their own tournaments (and the fee for doing so) is core, not optional — and that the create-fee amount must stay fully admin-controlled via `feeConfig`, never hardcoded. Implementation decision made alongside this: the fee itself debits instantly on submission (internal wallet spend), while the *tournament's* visibility still requires separate admin approval — only real-world deposit/withdrawal money needs admin review before affecting the wallet.
- **2026-07-29 — Prize payout stays manual/explicit:** rather than trying to auto-parse a tournament's free-text `prizeDistribution` field to calculate payout amounts, the admin specifies the exact amount per payout action. Revisit only if `prizeDistribution` is ever turned into a structured field (e.g. `[{ place, amount }]`).
- **2026-07-29 — Ban doesn't revoke live tokens:** banning a user blocks their *next* login, but an already-issued access token keeps working until it naturally expires (15 min default). Accepted tradeoff for MVP given the short access-token lifetime; would need a token-revocation/deny-list mechanism to close this gap fully.
- **2026-07-29 — Dev ports:** `royal-clans` runs on 3000 (Next.js default), `admin-panel` on 3001 (`next dev -p 3001`, set in its `package.json`) so both can run simultaneously in local dev. Backend CORS (`CLIENT_URLS` in `server/.env`) allow-lists both.
- **2026-07-29 — No client-side token refresh yet:** both frontends store only the access token; neither implements a "silently call `/auth/refresh` on 401" pattern yet, even though the backend supports it. Users simply have to re-login every 15 minutes for now. Intentional scope cut for MVP, not an oversight — revisit if a 15-minute re-login cadence proves annoying in real use.
- **2026-07-29 — Reset token returned in the API response (temporary):** with no email/SMS provider configured, `forgot-password` hands the raw token straight back in the response so the reset flow is fully testable end-to-end without email infra. This was a conscious, clearly-flagged tradeoff to keep the feature demoable — **not** a decision that this is fine for production. See the 🔴 SECURITY item under Known Issues; must be replaced with real delivery before real users exist.
- **2026-07-29 — Both apps get push, not just admin-panel:** user explicitly asked for both `royal-clans` and `admin-panel` to have push notifications (feel like an installed mobile app on both), plus Discord for admin-side alerts specifically, plus a spoken voice alert in the admin panel for incoming payment/tournament/dispute requests. All three were confirmed via an explicit clarifying question before building, rather than guessed.
- **2026-07-29 — Hand-rolled service worker, not `next-pwa`:** wrote `public/sw.js` manually (~30 lines, just `push`/`notificationclick` handlers) instead of adding a PWA plugin dependency. Reason: this project runs Next.js 16.2.11 (a recent/canary-adjacent version per its own `AGENTS.md` warning), and PWA plugins historically lag behind new Next major versions — a small manual service worker avoids a fragile dependency for a small amount of code.
- **2026-07-29 — Notification calls are fire-and-forget:** `notifyAdmins`/`sendPushToUser` calls in `wallet.service.ts`/`tournament.service.ts`/`match.service.ts` are deliberately not `await`ed by the calling code, so a slow or failing push/Discord call never delays or breaks the actual API response the user is waiting on. Internally they use `Promise.allSettled` so they never throw. Keep this pattern for any future notification call sites.
- **2026-07-29 — Room reuse is cooldown-based, not "mark busy / mark free":** a room is simply unavailable until `roomCooldownMinutes` have elapsed since `lastAssignedAt`. Chosen over an explicit busy/free flag because nothing in the system reliably knows when a real in-game lobby has actually emptied out — a time window needs no completion signal and can't leak a permanently-stuck "busy" room if a match is abandoned. Selection is least-recently-used so rotation is even.
- **2026-07-29 — Room credentials are stripped server-side, not hidden in the UI:** `listTournaments` uses a `-roomId -roomPassword` projection and `getTournamentById` deletes them from the response object unless the caller is entitled. Never rely on the frontend to hide them — an unauthenticated `curl` must not be able to see a lobby password. Added `optionalAuth` middleware specifically so the public detail route can vary its response by caller without forcing a token.
- **2026-07-29 — Tournament room ID/password required at create, but editable after:** the user asked for them at creation time, so the schema requires them. An organizer/admin-only `PUT /tournaments/:id/room` was added alongside because real room IDs are usually only known shortly before match time and a tournament scheduled days out would otherwise be stuck with a placeholder.
- **2026-07-29 — Official tournaments skip both the fee and the approval queue:** when an admin creates a tournament, the platform is simultaneously organizer and approver, so charging itself a create fee and then approving its own submission would be theatre. `isOfficial: true`, `createFeeCharged: 0`, `status: approved` immediately.
- **2026-07-29 — Quick Match polling is one mount-lifetime interval, not state-keyed:** the first implementation only polled while `state === "waiting"` and tore the interval down on every state change, which orphaned it and left an already-open page stuck on "Searching..." even after the backend had paired the player. Fixed by driving one interval through a ref for the component's whole life. Do not "optimize" this back into a conditional interval — continuous polling is also what makes the page live-update when the opponent submits their result.
- **2026-07-29 — The Quick Match page must re-fetch a finished match:** `GET /quick-match/status` only reports *active* matches, so a confirmed match vanishes from it and the page would silently return to the search form — meaning the winner never saw that they won. The component now remembers the match id it was in and re-fetches it once it disappears from status, to show a win/loss card. Any future change to what statuses `getMyStatus` returns must keep this in mind.
